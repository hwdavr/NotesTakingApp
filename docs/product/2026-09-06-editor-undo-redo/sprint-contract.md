# Sprint Contract — Note Editor Undo & Redo

## 🏃 Sprint Overview

* **Sprint:** `P10-01`
* **Feature:** Note Editor Undo & Redo
* **Duration:** 3 sequential implementation sessions
* **Plan revision:** Re-sliced on 2026-09-06 after user feedback: consolidated from four stories to three — the guardrail, persistence-lifecycle, reopen-journey, and visual-verification work is merged into one final US-3 slice.

## 🎯 Scope

### In Scope

* [ ] In-memory, session-scoped snapshot history over every body/document edit of the open note (title excluded), seeded at load/open and cleared on editor exit or process death.
* [ ] Undo/Redo through the existing editable default bottom-toolbar controls with enabled/disabled states (38% alpha disabled) and hardware-keyboard shortcuts (Ctrl+Z, Ctrl+Shift+Z, Ctrl+Y).
* [ ] Continuous-typing coalescing into single steps and exactly-one-step discrete actions for formatting marks, block operations, tables, charts, code, mermaid, formulas, links, emoji, images, and voice blocks.
* [ ] Caret/selection restoration to the changed block, cell, or field after undo/redo, with fallback focus to the nearest preceding block when the restored state has no such target.
* [ ] Voice/image undo that removes only the document block without touching the underlying file, and Redo that restores the block with its original id and path.
* [ ] Read-only exclusion: no history, no rendered controls, no shortcut effect; redo-tail truncation on any new edit; bounded 100-step history; history survives device rotation.
* [ ] Autosave/persistence semantics: undo/redo schedule autosave, leaving the note persists the visible (possibly undone) document, and reopening starts a fresh baseline with Undo/Redo disabled.
* [ ] Final in-test visual captures of the completed undo/redo toolbar states (baseline disabled, undo enabled, redo enabled, keyboard-visible, read-only absence) and a registered production journey.

### Out of Scope

* Title-field undo/redo (title is never part of history; Ctrl+Z while the title is focused acts on the shared document history).
* Persisting history across sessions, note reopen, or process death; history is never written to Room, DataStore, or files.
* Undo/redo of favorite/pin toggles, folder moves, note delete, rename-dialog outcomes, export, categorization, or sharing.
* New toolbar positions, icons, copy, bottom sheets, gesture undo, multi-document history, or collaboration.
* Any redesign of the editor shell or new dependencies.

## Dependency Order and Risk

The dependency order is linear: US-1 establishes the snapshot funnel, coalescer, pointer semantics, and live toolbar controls; US-2 proves exact one-step coverage across rich content kinds and cell/field focus restoration; US-3 adds shortcuts, read-only guards, session robustness, closes the persistence/lifecycle contract, registers the exit/reopen journey, and owns the final in-test visual evidence. The highest technical risk is US-1: a single commit funnel must wrap every document mutation path without regressing existing autosave, and coalescing must be deterministic and testable. Every slice remains observable through the already-reachable Undo/Redo buttons in the Note Editor.

## User Scenarios & Testing

### US-1: Session document history with typing undo/redo and toolbar states (Priority: P1)

A user opens an editable note, types into a body text block, and taps the existing Undo control: the typed run is removed in one step and the caret returns to the restored position. Redo replays the run; both controls enable and disable as history becomes available, and typing only in the title never creates history.

**Why this priority**: The snapshot funnel, coalescing rules, and pointer semantics are the foundation and the highest-risk part; they must be proven through the live Undo/Redo buttons before rich-content coverage is layered on.

**Independent Test**: Open the production editor on an editable note, type runs into a body block with controlled pauses, tap Undo and Redo repeatedly, type in the title only, and observe the button states and document text at every step; drive the same semantics through the ViewModel and pure history helper in JVM tests.

**Acceptance Criterion**:

1. **AC-US-1-01 Given** an editable note with typed text, **When** Undo is tapped, **Then** the previous document text is restored exactly (marks and content included) and the caret lands at the restored location; repeated Undo walks further back.
2. **AC-US-1-02 Given** an editable note with no document changes since it opened, **When** Undo or Redo is tapped, **Then** no document change occurs and both controls remain disabled.
3. **AC-US-1-03 Given** at least one undo, **When** Redo is tapped, **Then** the next forward text state is re-applied; at the history head Redo is a no-op and stays disabled.
4. **AC-US-1-04 Given** one or more undos, **When** a new text edit is made, **Then** the redo tail is discarded and the new edit becomes the next undo step.
5. **AC-US-1-05 Given** continuous typing into one block without a longer pause, **When** Undo is tapped once, **Then** the entire typing run is removed in a single step.
6. **AC-US-1-06 Given** two typing runs separated by a pause longer than the coalescing window, **When** Undo is tapped twice, **Then** each run is removed as its own step.
7. **AC-US-1-07 Given** a document history, **When** the toolbar renders, **Then** Undo is enabled exactly when history exists below the pointer and Redo exactly when a redo tail exists; otherwise each control is disabled with 38% alpha content and disabled semantics.
8. **AC-US-1-08 Given** a user types only in the title field, **When** Undo/Redo states are inspected, **Then** history stays empty, both controls remain disabled, and the document is unchanged.

### US-2: Undo discrete rich-content actions with exact restoration (Priority: P2)

A user applies formatting, inserts emoji or blocks, edits table/chart/code/mermaid content, and commits formula or link changes through the editor's sheets; every discrete action is exactly one undo step, and Undo/Redo restore byte-exact documents with focus and caret returned to the affected cell or field. Undoing an inserted voice or image block removes only the document block, never its file.

**Why this priority**: Rich-content kinds are where document identity, cell focus, and file-preservation rules live; they depend on the US-1 funnel and are the largest surface of possible regression.

**Independent Test**: In the production editor, mix typing with a Bold toggle, emoji insertion, a block insertion, and a table cell edit, then unwind with Undo; drive the ViewModel with voice/image, chart, code, mermaid, and overlay-committed fixtures and assert exact snapshots at every pointer position.

**Acceptance Criterion**:

1. **AC-US-2-01 Given** a sequence mixing typing, a Bold toggle, an emoji insertion, and a block insertion, **When** Undo is tapped repeatedly, **Then** each discrete action unwinds as its own step and every restored state equals the exact pre-edit document (marks, links, formulas, and block identities included).
2. **AC-US-2-02 Given** rich-content steps are undone, **When** Redo is used and a new rich edit is then made, **Then** Redo replays the exact forward states until the new edit truncates the redo tail.
3. **AC-US-2-03 Given** an undo removes the block that held focus, **When** the undo completes, **Then** focus moves to the nearest preceding block, or clears when no block remains, without any crash or dangling focus.
4. **AC-US-2-04 Given** text typed inside a table cell, chart data cell, code field, or mermaid field, **When** Undo is applied, **Then** the cell/field regains focus with the recorded caret/selection and same-target typing coalesces per field.
5. **AC-US-2-05 Given** an inserted Voice or Image block is undone, **When** the undo completes and Redo is then used, **Then** only the document block is removed (no audio/image file is deleted) and Redo restores the block with its original id and file path.
6. **AC-US-2-06 Given** a formula or link change is committed from an overlay flow, **When** the editor is inspected after the overlay closes, **Then** that committed change is the next undo step and unwinds exactly.

### US-3: Shortcuts, guardrails, persistence lifecycle, reopen journey, and final visual verification (Priority: P3)

A user on a hardware keyboard presses Ctrl+Z, Ctrl+Shift+Z, or Ctrl+Y to undo and redo from anywhere in the editor; read-only notes expose no history, no controls, and no shortcut effect; history survives device rotation, stays bounded, and works with the soft keyboard open. Undo/redo schedule autosave, exiting the note persists the undone document, and reopening starts a fresh baseline with both controls disabled. This final slice captures the completed visual states inside a dedicated VisualFlowTest and registers the exit/reopen production journey.

**Why this priority**: Shortcut dispatch, read-only guards, rotation, persistence-after-undo, and the completed-flow visual contract are cross-cutting behavior that must close the feature; US-3 is the natural final user-reachable state for the sole visual-verification owner and the exit/reopen journey.

**Independent Test**: On a hardware-keyboard emulator, type and use each shortcut combination from the body and the title field; open a read-only note and repeat the combos; rotate the device mid-history; fill history past its cap in the JVM helper; undo with the soft IME visible; then type, undo, exit, and reopen the note to check the persisted content, disabled controls, and every in-test visual capture.

**Acceptance Criterion**:

1. **AC-US-3-01 Given** a read-only note is open, **When** the toolbar and keyboard shortcuts are exercised, **Then** no Undo/Redo controls are rendered and Ctrl+Z/Ctrl+Shift+Z/Ctrl+Y produce no document change.
2. **AC-US-3-02 Given** a note becomes read-only mid-session after an edit, **When** undo/redo are invoked, **Then** they are no-ops, canUndo/canRedo read false, and no new history step is recorded.
3. **AC-US-3-03 Given** an editable note with history, **When** Ctrl+Z, Ctrl+Shift+Z, and Ctrl+Y are pressed from the body or the title field, **Then** Ctrl+Z undoes, each redo combo replays, and the shared document history is used regardless of the focused field.
4. **AC-US-3-04 Given** an editable note at baseline or with only a title change, **When** the shortcut combos are pressed, **Then** no document change occurs and the combos are not consumed as undo actions.
5. **AC-US-3-05 Given** typed text and one undo, **When** the device rotates (activity recreation), **Then** the document keeps the undone state, Redo remains enabled, and Redo still restores the typed text.
6. **AC-US-3-06 Given** a history exceeding 100 steps, **When** the cap is enforced, **Then** the oldest snapshots are evicted and the current state and pointer remain valid.
7. **AC-US-3-07 Given** the soft IME is visible while typing, **When** Undo is tapped, **Then** the text is undone, the 56dp bottom toolbar with Undo/Redo remains visible above the keyboard, and nothing overlaps the focused field.
8. **AC-US-3-08 Given** a pending Bold typing mark followed by text, **When** Undo and then Redo are applied, **Then** pendingTypingMarks is empty afterwards and subsequently typed text carries no stale Bold mark.
9. **AC-US-3-09 Given** an editable note with typed text that was undone, **When** the user exits the note and reopens it, **Then** the reopened note shows the undone content and Undo/Redo are disabled, proving a fresh baseline whose content is the saved state.
10. **AC-US-3-10 Given** an undo without any further edit, **When** the existing autosave path runs, **Then** the repository receives the currently visible (undone) document as the note content.
11. **AC-US-3-11 Given** an editable note at its loaded baseline, **When** the completed flow is captured, **Then** the dedicated visual test produces a non-empty screenshot showing both Undo/Redo controls disabled (38% alpha) with disabled semantics.
12. **AC-US-3-12 Given** an editable note after one typed edit, **When** the completed flow is captured, **Then** the dedicated visual test produces a non-empty screenshot showing Undo enabled and Redo disabled.
13. **AC-US-3-13 Given** an editable note after one undo, **When** the completed flow is captured, **Then** the dedicated visual test produces a non-empty screenshot showing Redo enabled over the undone content.
14. **AC-US-3-14 Given** an editable note with the IME visible, **When** the completed flow is captured, **Then** the dedicated visual test produces a non-empty screenshot showing the 56dp bottom toolbar with Undo/Redo above the keyboard, not overlapping the focused field.
15. **AC-US-3-15 Given** a read-only note, **When** the completed flow is captured, **Then** the dedicated visual test produces a non-empty screenshot showing the read-only bottom bar without Undo/Redo controls.
